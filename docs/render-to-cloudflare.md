# RI BUROM hosting transfer from Render to Cloudflare

**Operator runbook · 23 November 2026 · Application baseline `f9bebee`**

## Current decision · Replace Render on Cloudflare Free

The hosting budget is zero, including usage overages. Move the Flask web service and background delivery off Render. Keep the existing Neon PostgreSQL database, Brevo email and Cloudinary media. Keep Cloudflare on Workers Free. The previous Containers proposal below is archived because it requires Workers Paid. Its Dockerfile is a local draft.

| Component | Free-plan assessment for RI BUROM |
| --- | --- |
| Database | D1 Free uses SQLite semantics and permits 500 MB per database, 5 GB across the account, 5 million rows read and 100,000 rows written per day. The current application uses Neon PostgreSQL via SQLAlchemy. A D1 move requires a database-access port, data conversion, and tests of transactions and concurrent updates. D1's 2 MB row limit also prevents a direct import of larger review attachments. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) · [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/) |
| Photos, videos and PDFs | R2 Standard includes 10 GB-month of storage, 1 million Class A operations and 10 million Class B operations monthly. Excess usage is billable. Under a strict zero-charge policy, leave R2 disabled unless an enforceable zero-spend ceiling specifically covering R2 is verified. An alert alone is insufficient. Keep Cloudinary assets and private review attachments in place while verifying existing plans. [R2 pricing](https://developers.cloudflare.com/r2/pricing/) |
| Web application | Workers Free supports Flask through its WSGI adapter and allows 100,000 requests/day with 10 ms CPU per invocation. Prototype with synthetic data. Verify the database driver, email retry scheduling, image processing, private video access and Word export under these limits before considering a cutover. [Flask on Workers](https://developers.cloudflare.com/workers/languages/python/packages/flask/) · [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) |

### Free hosting implementation and test status

Use a thin Python Worker to serve or forward requests to a SQLite-backed Durable Object running the Flask WSGI application. The Durable Object's SQLite storage can hold rate-limit counters. Keep customer records and review attachments in Neon. Serve repository static assets through Workers Static Assets. Use Hyperdrive to pool the Neon connection and start with query caching disabled so the Control Room can read its own writes. This is a hosting port with the same PostgreSQL data model. [Durable Object limits](https://developers.cloudflare.com/durable-objects/platform/limits/) · [Python Hyperdrive](https://developers.cloudflare.com/hyperdrive/examples/python-workers/) · [Hyperdrive Free quota](https://developers.cloudflare.com/hyperdrive/platform/pricing/)

Local Wrangler tests against the existing Flask routes and synthetic fixtures returned HTTP 200 for the homepage, liveness, readiness, review photo processing and Word invoice generation. SQLAlchemy with `pg8000` executed a query on an isolated PostgreSQL 18 instance. Pyodide lacks the application's native `hashlib.scrypt`; a PyCryptodome adapter passed a synthetic scrypt generation and verification round-trip. The existing in-memory Flask-Limiter backend failed at import because it starts a Python thread. A replacement using Durable Object SQLite returned 200 for the first three requests and 429 for the fourth. These experiments ran in a disposable copy. The repository's production runtime and login code are still the current Flask implementation.

Before production, validate startup time and memory on the actual Free plan, and verify the existing password hash format across runtimes. Test the storage adapter's expiry cleanup and isolate restart. Use a short scheduled Worker handler to invoke a bounded outbox job inside a Durable Object so Brevo and IndexNow do not depend on web traffic. Keep PostgreSQL connections scoped to requests. Test delivery and retries with test recipients, then check representative media sizes, review visibility, staff sessions, invoice downloads and behaviour after an idle period. Free quota exhaustion can interrupt requests. Measure both the Worker and Durable Object daily usage during staging. [Durable Object Free quotas](https://developers.cloudflare.com/durable-objects/platform/pricing/) · [Workers Free limits](https://developers.cloudflare.com/workers/platform/limits/)

Wrangler deployed a synthetic staging build into the verified RI BUROM Cloudflare account. The first build returned HTTP 503 with Cloudflare error 1105 for dynamic requests. Deferring Flask imports to the Durable Object resolved the observed failure. The second build passed HTTPS checks for the homepage, readiness, static CSS, synthetic password verification, photo processing, Word invoice generation and rate-limit enforcement. Staging uses a disposable SQLite fixture and has no production service credentials. [Staging preview](https://riburom-free-compatibility-probe.dakhroo.workers.dev/)

The staging Worker also reached a separate empty Neon Free project through cache-disabled Hyperdrive. A Cron Trigger retried a deliberately failed outbox job and recorded success on attempt two using a simulated Brevo transport. Real Brevo delivery, live Cloudinary uploads and the production Neon connection still need end-to-end verification.

The staging Worker configuration and Python packaging are on GitHub at `codex/cloudflare-free-hosting`. Cloudflare Workers Builds can build this branch and invokes the Wrangler deployment command. The production release and DNS switch are a separate cutover. Retire Render after the production web app and background delivery job pass independently on the canonical domain. [GitHub integration](https://developers.cloudflare.com/workers/ci-cd/builds/git-integration/github-integration/) · [Build configuration](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/)

## Archived alternative · Paid Containers (outside current scope)

The following procedure describes the earlier paid proposal. It moves the Flask web service to Cloudflare Containers while retaining Neon, Brevo and Cloudinary. It is reference material only under the current budget.

This is a proposed procedure. The repository inspection establishes the application requirements. The operator must confirm the current service settings, DNS authority, billing plan, provider restrictions, and backup retention in the respective dashboards. No infrastructure has been provisioned by this runbook.

## 1. Decide what moves

| Component | Destination and handling |
| --- | --- |
| HTTP application | A Cloudflare Worker forwards requests to a Linux container running Python 3.14.3 and Gunicorn. The Flask routes, Jinja templates, native Python dependencies, and Word export stay together. A static Pages upload alone cannot serve the Control Room or process forms. |
| Database | Use the existing Neon PostgreSQL production branch at cutover. It holds users, enquiries, invoices, reviews, and notification jobs. The `review_attachments.content` column also holds the actual review photo and video bytes. |
| Public media | Keep the same Cloudinary environment, asset IDs, delivery URLs and permissions for existing tour photos, CMS videos and uploaded PDFs. Ship Git-tracked static files, including the favicon and invoice logo, in the container image. |
| Business email | Keep Brevo and its authenticated sender. Flask commits an enquiry and an outbox record to Neon. A delivery process calls Brevo over HTTPS. Moving the web service requires an explicit plan for that process. |
| Domain and mail | Keep `riburomtours.com`, current canonical redirects, mailbox provider and registrar. DNS hosting can move separately if needed. Brevo transactional sending and incoming mailbox delivery are distinct services. |

**Why Containers:** the release already runs `wsgi:app` and uses PostgreSQL drivers, Pillow and python-docx. Containers retain that Linux runtime. Cloudflare requires Workers Paid for Containers. Budget for the plan, Worker and Durable Object usage, container CPU, allocated memory and disk while running, network usage as applicable, and temporary Render overlap. Estimate costs from observed traffic and uptime before authorising cutover. [Containers overview](https://developers.cloudflare.com/containers/) · [Pricing](https://developers.cloudflare.com/containers/platform/pricing/) · [Instance limits](https://developers.cloudflare.com/containers/platform/limits/)

## 2. Record the current production baseline

1. **Release owner:** record the deployed Git SHA from Render, Python version, build and start commands, region, instance count, Gunicorn settings, autosuspend behaviour, custom domains, scheduled jobs and auto-deploy settings. The repository documents one instance and one worker. Compare those values to the live dashboard.
2. **DNS owner:** export the authoritative zone. Record apex and `www` targets, proxy flags, redirect direction, TTLs, certificate status, CAA, nameservers and DNSSEC/DS state. Inventory MX, SPF, DKIM selectors, DMARC, Brevo verification records, search-verification records and unrelated subdomains. Capture a working external mail send/receive baseline.
3. **Database owner:** record the Neon project, production branch, database, region, connection mode and current Alembic revision. Confirm a usable recovery point and rehearse recovery on an isolated branch. Compare representative row counts and identifiers for enquiries, invoices, reviews, attachments and outbox states. Keep customer data and credentials out of the release ticket.
4. **Operations owner:** capture baseline homepage and Control Room latency, error rate, oldest pending email, failed deliveries, and examples of a working Cloudinary photo and PDF. Record who can switch traffic back and who can check the recipient inbox. Confirm dashboard access for GitHub, Render, Cloudflare, Neon, Brevo and Cloudinary before the change window.

## 3. Build the Cloudflare release in staging

The inspected release has a Render Procfile. The following **deployment files and automation still need to be implemented and tested** before traffic moves.

1. On a deployment branch, add a Dockerfile and a restrictive Docker build context. Use a compatible Linux Python 3.14.3 image, install the pinned requirements, include templates, static files, migrations and scripts, and start one Gunicorn worker. For an internal port of 8080 the command is `gunicorn --bind 0.0.0.0:8080 --workers 1 wsgi:app`. Exclude local databases, uploads, Git metadata, credentials and environment files. Record the built image digest.
2. Use Cloudflare’s current Containers starter to create the Worker, Durable Object binding, Wrangler configuration and binding migration. Configure the same internal port and route traffic initially to **one stable named instance**. The Worker must wait for the port and forward method, path, query string, body, cookies, redirects, response headers and byte-range requests. Preserve separate `Set-Cookie` headers. Enable outbound internet for the container and test PostgreSQL TCP/TLS as well as provider HTTPS. [Container setup](https://developers.cloudflare.com/containers/get-started/) · [Routing and scaling](https://developers.cloudflare.com/containers/configuration/scaling-and-routing/) · [Outbound networking](https://developers.cloudflare.com/containers/configuration/outbound-traffic/)
3. Use a separate staging Worker, container binding and secrets. Protect its hostname with Cloudflare Access and disable public indexing. Point it to a disposable Neon branch or sanitised test database, a separate Cloudinary test environment, and a controlled Brevo recipient. A Neon copy can include queued **production** email, phone recipients, and IndexNow payloads. Keep all consumers disabled until copied jobs are removed on the verified staging branch and test records have been created. Use a distinct staging session key. Keep staging away from production media deletion and customer messaging.
4. Build the Docker image without production credentials. Run CI, then rehearse the migration once in a release job using the same code and runtime. Deploy to staging with `npx wrangler deploy --env staging` after defining that environment. Use a protected production release job, scoped Cloudflare credentials, a pinned Wrangler version and an immutable Git SHA for production. [Wrangler configuration](https://developers.cloudflare.com/workers/wrangler/configuration/)
5. At the edge, overwrite forwarded IP and scheme headers from trusted Cloudflare request metadata and preserve the intended public host. The app trusts exactly one hop when `TRUST_PROXY_HEADERS=true`. Verify secure redirects, real visitor IPs in rate limits, CSRF and staff sessions. Bypass shared caching for HTML with forms, staff pages, invoices, previews, enquiry responses and `/reviews/media/*`. Respect the application's private/no-store responses. Cache only suitable static assets initially.

### Migration and background delivery

**Schema release:** from the repository root, run `python scripts/debug_migration.py` once in a controlled release job before enabling the new application. The script connects to PostgreSQL, upgrades Alembic and checks bootstrap defaults. Validate `SELECT version_num FROM alembic_version;` against the release head. At the inspected SHA the expected head is `ea4cd9f32108`. An established production database should already have an Alembic version table. If the preflight shows a missing table or unexpected database identity, stop and verify the connection. Never put this script in the Docker image build or per-instance startup. Freeze Render auto-deploys during the production change so two platforms cannot launch migration gates concurrently.

**Outbox release:** the present web process starts a background thread after its first request. Idle or stopped containers cannot reliably provide that retry loop. The recommended target is a Cloudflare Cron Trigger with a private, authenticated application job that processes a bounded batch using the logic in `scripts/process_notification_outbox.py`. Implement the scheduled handler and internal invocation, including timeout, overlap control and failure reporting. Cron invokes a Worker handler; it cannot run a Python shell command inside the web container by itself. An alternative is a dedicated persistent runner for the existing management command. Select and prove one approach before switching off the Render consumer. [Cloudflare Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)

With an independent consumer, set `OUTBOX_WORKER_ENABLED=false` in the Cloudflare **web** process. Initially leave the existing Render consumer responsible for production delivery. At handoff, finish or allow existing claims to expire, disable that consumer and activate the verified replacement. The manual command is `python scripts/process_notification_outbox.py --limit 50`. Inspect its sent/failed/skipped summary and database states. A successful process exit alone does not prove delivery. Alert on growing queue age and failures. Test a retry while the website receives no traffic. Delivery is at least once, so reconcile the Brevo log before manually replaying uncertain sends.

## 5. Switch production traffic

1. **Prepare DNS independently.** If the zone already uses Cloudflare authoritative DNS, verify the existing records in place. Otherwise import the complete zone, compare it to the export, and follow the documented DNSSEC sequence at the registrar before changing nameservers. Allow delegation to settle with the website still served by Render. Keep mail hosts DNS-only where required and preserve all authentication records. Verify inbound mail, Brevo sender authentication and HTTPS on apex and `www` before the hosting cutover. [Cloudflare DNS onboarding](https://developers.cloudflare.com/dns/zone-setups/full-setup/setup/)
2. **Establish the rollback route.** For the change window, retain the proxied DNS record pointing to the verified Render origin, its custom-domain mapping and valid certificate. Verify Full (strict) TLS to Render. Configure the Cloudflare Worker using **Workers Routes** on the existing proxied hostname. A route can intercept the hostname while the DNS record still identifies Render as the origin. Record the previous routing and cache rules. [Workers Routes](https://developers.cloudflare.com/workers/configuration/routing/routes/)
3. **Deploy the same release to Cloudflare.** Freeze unrelated releases. Run the production identity and migration checks, deploy the tested image and verify readiness. Confirm that Render can still run against the same schema. Defer incompatible schema changes to a later release.
4. **Switch the route.** Bind the tested Worker to `riburomtours.com/*` and handle `www` according to the existing redirect policy. Confirm the Worker forwards to the container, then verify the request in Cloudflare logs. Check the public homepage, existing media, staff login and readiness through the real domain. Complete the consumer handoff and check a controlled Brevo delivery.
5. **Observe and sign off.** Watch HTTP errors, latency, memory, cold starts, Neon connections, queue age, Brevo delivery, Cloudinary errors and estimated cost. Keep both origins and their configuration recoverable through an agreed observation period covering normal traffic and an idle/retry cycle. Record Git SHA, image digest, schema revision, route switch time, evidence, and the operator approving retirement.

## 6. Roll back or retire Render

**Roll back immediately** for sustained readiness failures, broken login or CSRF, lost enquiry writes, exposure of private content, or a growing delivery backlog without a working consumer. The release owner removes or disables the new Worker route so the existing proxied DNS record serves Render again. Restore the previous redirect and cache rules if changed. If a custom-domain binding was used instead, restore the saved Render DNS target and custom-domain mapping and allow for DNS propagation.

Stop the Cloudflare consumer and resume the Render consumer. Confirm readiness, a retained post-cutover enquiry, private media access controls and Brevo queue processing. Both origins use the same Neon database, so writes accepted during the change remain available. A hosting rollback normally needs no Neon restore or Alembic downgrade. Database recovery is a separate incident decision because restoring a snapshot can discard later enquiries and invoices.

**Retire Render only after sign-off.** Replace the temporary Render-backed routing arrangement with a tested permanent Cloudflare Worker Custom Domain for the canonical host, following Cloudflare's procedure for conflicting DNS records and existing routes. Preserve the approved `www` behaviour and test TLS and the full request path again before removing the Render domain, instances, jobs or billing. Verify that the Cloudflare release pipeline and independent outbox consumer work with Render stopped. Remove Render-specific deployment access, then rotate any shared credential through the target service in a coordinated change. Keep a record of the last working image and Worker deployment for later rollbacks. [Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)
